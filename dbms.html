Chapter 01

Introduction to DBMS

Foundations, architecture, users, and why file systems fall short.

⏱ ~25 min read

1.1 Overview & Definition

⭐ Exam Favourite — Definition of DBMS asked in 2-mark & 5-mark questions.
Definition

DBMS (Database Management System) is a software system that manages, stores, and retrieves data efficiently in a structured format. It allows users to create, update, and query databases, ensures data integrity & consistency, reduces redundancy, and supports concurrent access.

Database

An organized collection of related information that can be searched, sorted, and updated — typically stored electronically and accessed via a DBMS using SQL.

💡
Analogy: Think of DBMS as a smart librarian — it knows where every book (data) is, controls who can access it, and can retrieve any book instantly.

How DBMS Works — API Bridge

👤 User / App

→

→
Database

Users never touch the database directly. The DBMS validates, authorizes, and retrieves data safely.

1.2 File System Drawbacks

🔴 Very Important — Often asked for 5 marks. List & explain any 5.
♻
Data Redundancy

Same data stored in multiple files, wasting storage and causing inconsistencies.

⚠
Data Inconsistency

Updating one file but not others leads to conflicting data across the system.

🔒
Poor Security

No built-in access control; any user can potentially access sensitive files.

⚛
Atomicity Issues

Partial transactions (e.g., debit without credit) cannot be automatically rolled back.

🔗
Data Isolation

Scattered files in different formats make it hard to write retrieval programs.

👥
No Concurrency

Two users cannot safely update the same file simultaneously.

File System vs DBMS
AspectFile SystemDBMS
Data RedundancyHighEliminated via normalization
Backup & RecoveryManual / NoneBuilt-in tools
Concurrent AccessSingle userMulti-user with locking
SecurityVery lowAuthentication & ACL
Data IndependenceNoneLogical & Physical
Query ProcessingInefficientOptimized query engine

1.3 Advantages of DBMS

  1. Data Security — Access control & encryption protect sensitive data.
  2. Data Integration — Centralizes data from multiple sources for a unified view.
  3. Data Abstraction — Hides internal complexity from end users.
  4. Reduced Redundancy — Unique constraints eliminate duplicate records.
  5. Data Sharing — Multiple applications and users share the same data.
  6. Data Consistency & Accuracy — Integrity constraints sync updates across views.
  7. Efficient Access — Indexing & query optimization for fast retrieval.
  8. Scalability — Easily handles growing data volumes.
📝 Disadvantages: High cost (hardware + staff), complexity, performance issues for small firms, frequent upgrades needed.

1.6 Structure / Components of DBMS

⚙
Query Processor

Interprets user queries. Contains DML Compiler, DDL Interpreter, Query Optimizer, Embedded DML Pre-compiler.

💾
Storage Manager

Interface between data & queries. Contains Authorization Manager, Integrity Manager, Transaction Manager, File Manager, Buffer Manager.

🗄
Disk Storage

Contains Data Files (actual data), Data Dictionary (metadata), and Indices (fast retrieval).

❓ Viva & FAQ — Chapter 1

A database is the organized collection of data. A DBMS is the software that manages, stores, and retrieves that data. The database is the data; the DBMS is the tool to handle it.

The ability to change the schema at one level without affecting the schema at the next higher level. Two types: Physical (change storage without affecting logical) and Logical (change logical without affecting view).

DBA defines schema, creates user accounts, controls access (GRANT/REVOKE), monitors backups, handles security breaches, and repairs hardware/software failures.

3.2 Types of Keys

⭐ Keys are asked in every exam! Memorize definitions + differences.
🗝
Primary Key

Uniquely identifies each tuple. Must be unique and NOT NULL. Only one per table.

🔑
Candidate Key

Set of attributes that can uniquely identify a tuple. Minimal superkey. There can be multiple.

🔓
Super Key

Any set of attributes that uniquely identifies a tuple. May have extra attributes.

🔗
Foreign Key

Attribute in one table referring to the Primary Key of another. Enforces referential integrity.

🔐
Composite Key

Two or more attributes combined to uniquely identify a tuple.

✨
Unique Key

All values must be distinct. Unlike PK, CAN contain one NULL. Multiple per table allowed.

FeaturePrimary KeyUnique KeyForeign Key
NULL allowed?NoYes (one)Yes (if allowed)
How many per table?Only oneMultipleMultiple
PurposeIdentify rowsPrevent duplicatesLink tables

3.3 Constraints in Relational Model

  1. Domain Constraints — Each attribute value must be atomic and from its defined domain (INT, VARCHAR, DATE…).
  2. Key Integrity — Every relation must have a key; it must be unique and NOT NULL.
  3. Referential Integrity — Foreign key values must match existing primary key values in the referenced table.
  4. Check Constraints — Values must satisfy a logical condition (e.g., age ≥ 18).

3.4 Anomalies

➕
Insertion Anomaly

Cannot insert data unless other (unrelated) data is also present. E.g., can't add a new course until a student enrolls.

🗑
Deletion Anomaly

Deleting one record unintentionally removes other important data. E.g., deleting last student in a course removes the course info too.

✏
Update Anomaly

Same data in many rows — updating only some leads to inconsistency. E.g., changing a name in one row but not others.

💡
Anomalies are solved by Normalization — splitting tables to reduce redundancy.

Chapter 04

Normalization & Functional Dependencies

FDs, Armstrong's axioms, closure, candidate keys, 1NF, 2NF, 3NF.

⏱ ~35 min read

4.1 Functional Dependencies

Definition

An FD X → Y means: for any two tuples t₁, t₂ in relation R, if t₁[X] = t₂[X] then t₁[Y] = t₂[Y]. In other words, X determines Y.

📌
Example: RollNo → Name, Branch, Year (one roll number has exactly one name, one branch, one year).

Armstrong's Axioms (sound & complete)

A1
Reflexivity: If Y ⊆ X, then X → Y
A2
Augmentation: If X → Y, then XZ → YZ
A3
Transitivity: If X → Y and Y → Z, then X → Z

4.2 Design Pitfalls

♻
Redundancy

Same fact stored in many rows. Name repeated for every course of the same student.

➕
Insertion Anomaly

Can't store a new course until a student enrolls.

🗑
Deletion Anomaly

Deleting last row of a course removes course info permanently.

✏
Update Anomaly

Updating name in one row while others remain with old value → inconsistency.

4.3 Attribute Closure (X⁺)

⭐ Algorithm for X⁺ is a guaranteed exam question. Practise with examples!
Definition

The closure of attribute set X (X⁺) is the set of all attributes that are functionally determined by X using the given FD set F.

Algorithm:

1
Initialize: X⁺ := X
2
Repeat: For each FD Y → Z in F, if Y ⊆ X⁺, add Z to X⁺
3
Stop when no new attribute can be added
📝 Solved Example

R(A,B,C,D) with FDs: A→B, B→C, CD→A. Find A⁺.

Start:    A⁺ = {A}
A → B  ⇒ A⁺ = {A, B}
B → C  ⇒ A⁺ = {A, B, C}
CD → A: need D but D ∉ A⁺ → cannot apply
Result:   A⁺ = {A, B, C}
💡
Uses of X⁺: (1) Check if X is a superkey — if X⁺ = all attributes. (2) Check if FD X→Y holds — if Y ⊆ X⁺. (3) Find candidate keys.

4.4 Finding Candidate Keys

1
Find attributes that never appear on RHS of any FD → Start with these as K
2
Compute K⁺ — if it covers all attributes, K is a superkey
3
If not, add attributes from (R – K) one by one until closure covers all
4
Remove unnecessary attributes from K to make it minimal → Candidate Key
📝 Solved Example

R(A,B,C,D,E) FDs: A→B, B→C, CD→E, E→A. Find candidate key.

RHS attrs = {B,C,E,A} → D never appears on RHS → K = {D}
D⁺ = {D} — not all attributes, so add A
(A,D)⁺:
  Start: {A,D}
  A→B ⇒ {A,B,D}
  B→C ⇒ {A,B,C,D}
  CD→E ⇒ {A,B,C,D,E}  ✓ All attributes!
AD is a superkey.
Check minimality: A⁺={A,B,C}≠all, D⁺={D}≠all
∴ AD is minimal → Candidate Key = {A,D}

4.5 First Normal Form (1NF)

Definition

A relation is in 1NF if every attribute value is atomic (no multi-valued or nested attributes) and each row is unique.

❌ NOT in 1NF

Student(RollNo, Name, Phones) — where Phones = "98765, 91234" (multi-valued).

✅ In 1NF

StudentPhone(RollNo, Phone) — each (RollNo, Phone) pair is a separate row.

4.6 Second Normal Form (2NF)

Definition

A relation is in 2NF if it is in 1NF AND every non-prime attribute is fully functionally dependent on the entire candidate key (no partial dependency).

📌 Partial Dependency: A non-prime attribute depends on only part of a composite key.
📝 Example

Enroll(SID, CourseID, SName, Dept) — Key: (SID, CourseID)
FD: SID → SName, Dept ← Partial dependency! SName depends only on SID.

Fix: Decompose into Student(SID, SName, Dept) + Enroll(SID, CourseID)

4.7 Third Normal Form (3NF)

Definition

A relation is in 3NF if it is in 2NF AND there is no transitive dependency of a non-prime attribute on a candidate key. For every FD X→A, either X is a superkey OR A is a prime attribute.

📝 Example

Emp(EmpID, DeptID, DeptName) — EmpID→DeptID, DeptID→DeptName
Transitive: EmpID → DeptID → DeptName

Fix: Emp(EmpID, DeptID) + Dept(DeptID, DeptName)

Normal Forms Summary
NFConditionEliminates
1NFAtomic values, unique rowsMulti-valued attributes
2NF1NF + No partial dependencyPartial dependencies
3NF2NF + No transitive dependencyTransitive dependencies

✏

5.3 DDL Commands in Detail

-- CREATE TABLE
CREATE TABLE Student (
  RollNo   INT         PRIMARY KEY,
  Name     VARCHAR(40) NOT NULL,
  Branch   VARCHAR(20),
  Year     INT         CHECK (Year BETWEEN 1 AND 3),
  Email    VARCHAR(50) UNIQUE
);

-- ALTER: Add column
ALTER TABLE Student ADD Phone VARCHAR(15);

-- ALTER: Modify column
ALTER TABLE Student MODIFY Year TINYINT;

-- ALTER: Drop column
ALTER TABLE Student DROP COLUMN Email;

-- DROP TABLE (permanent!)
DROP TABLE Student;

-- TRUNCATE (removes data, keeps structure)
TRUNCATE TABLE Student;

5.4 DML Commands in Detail

-- INSERT
INSERT INTO Student (RollNo, Name, Branch, Year)
VALUES (1, 'Rohan', 'CS', 1);

-- UPDATE (always use WHERE!)
UPDATE Student
SET Year = 2
WHERE RollNo = 1;

-- DELETE (always use WHERE!)
DELETE FROM Student
WHERE Year = 3;

-- SELECT with DISTINCT
SELECT DISTINCT Branch
FROM Student;

-- SELECT with sorting
SELECT RollNo, Name, Year
FROM Student
ORDER BY Year DESC, Name ASC;
⚠ Without WHERE in UPDATE or DELETE, all rows are affected!

5.6 IN, NOT IN, BETWEEN, LIKE

-- IN: match any value in a list
SELECT * FROM Student WHERE Department IN ('CS', 'IT');

-- NOT IN: exclude values in list
SELECT * FROM Student WHERE Department NOT IN ('Finance');

-- BETWEEN: inclusive range
SELECT * FROM Student WHERE Marks BETWEEN 70 AND 90;

-- LIKE: pattern matching
SELECT Name FROM Student WHERE Name LIKE 'A%';    -- starts with A
SELECT Name FROM Student WHERE Name LIKE '%a';    -- ends with a
SELECT Name FROM Student WHERE Name LIKE '_a%';   -- 2nd letter is a
SELECT Name FROM Student WHERE Name LIKE '%oo%';  -- contains 'oo'
🎯
LIKE wildcards: % = any number of chars | _ = exactly one char

5.7 NULL Values in SQL

Definition

NULL means the absence of a value — it is NOT zero and NOT an empty string. You cannot use =, <, > with NULL. Use IS NULL or IS NOT NULL.

-- Check for NULL values
SELECT * FROM Customers WHERE SALARY IS NULL;
SELECT * FROM Customers WHERE SALARY IS NOT NULL;

-- Update NULL values
UPDATE Customers SET SALARY = 9000 WHERE SALARY IS NULL;

Chapter 06

Advanced SQL

Aggregate functions, GROUP BY, HAVING, Set operations, Joins, and Subqueries.

⏱ ~35 min read

6.1 Aggregate Functions

Definition

Aggregate functions compute a single value from many rows (whole table or per group). Usually used with GROUP BY.

-- COUNT all students
SELECT COUNT(*) AS NumStudents FROM Student;

-- Average salary per department
SELECT DeptID, AVG(Salary) AS AvgSalary
FROM Employee
GROUP BY DeptID;

-- MAX and MIN marks
SELECT MAX(Marks) AS Highest, MIN(Marks) AS Lowest FROM Result;

6.2 GROUP BY, HAVING, ORDER BY

⭐ GROUP BY + HAVING + ORDER BY is asked in almost every practical/theory exam.
🎯
Key rule: GROUP BY forms groups → HAVING filters groups → ORDER BY sorts the result.
-- Branches with avg percentage ≥ 60, sorted by avg
SELECT Branch, AVG(Percentage) AS AvgPercent
FROM Result
GROUP BY Branch
HAVING AVG(Percentage) >= 60
ORDER BY AvgPercent DESC;

-- WHERE filters rows BEFORE grouping
-- HAVING filters groups AFTER aggregation
ClauseWhen AppliedCan Use Aggregates?
WHEREBefore GROUP BY (row level)No
HAVINGAfter GROUP BY (group level)Yes
ORDER BYLast (on final result)Yes

6.3 Set Operations

∪
UNION

All distinct rows from both queries. UNION ALL keeps duplicates.

∩
INTERSECT

Only rows that appear in both result sets.

∖
EXCEPT / MINUS

Rows from first query NOT in second. (Oracle uses MINUS)

-- Students in CS or IT courses
SELECT RollNo FROM Enroll WHERE CourseID LIKE 'CS%'
UNION
SELECT RollNo FROM Enroll WHERE CourseID LIKE 'IT%';

-- Students in BOTH CS and IT
SELECT RollNo FROM Enroll WHERE CourseID LIKE 'CS%'
INTERSECT
SELECT RollNo FROM Enroll WHERE CourseID LIKE 'IT%';

-- Students in CS but NOT IT
SELECT RollNo FROM Enroll WHERE CourseID LIKE 'CS%'
EXCEPT
SELECT RollNo FROM Enroll WHERE CourseID LIKE 'IT%';

6.4 Joins

🔴 Very Important — Joins are 5–10 mark questions. Know all 4 types!
Join TypeReturnsNULLs?
INNER JOINMatching rows from both tablesNo NULLs
LEFT OUTER JOINAll left rows + matching right rowsRight side NULLs if no match
RIGHT OUTER JOINAll right rows + matching left rowsLeft side NULLs if no match
FULL OUTER JOINAll rows from both tablesNULLs on unmatched sides
 
-- INNER JOIN: only enrolled students
SELECT s.RollNo, s.Name, e.CourseID
FROM Student s
INNER JOIN Enroll e ON s.RollNo = e.RollNo;

-- LEFT JOIN: all students (unenrolled show NULL)
SELECT s.RollNo, s.Name, e.CourseID
FROM Student s
LEFT JOIN Enroll e ON s.RollNo = e.RollNo;

-- RIGHT JOIN: all courses (even with no students)
SELECT c.CourseID, c.Title, e.RollNo
FROM Enroll e
RIGHT JOIN Course c ON e.CourseID = c.CourseID;

6.5 Subqueries (Nested Queries)

Definition

A subquery is a SELECT statement written inside another SQL statement. The inner query runs first; its result is used by the outer query.

-- Scalar subquery: above average marks
SELECT RollNo, Name, Percentage
FROM Result
WHERE Percentage > (SELECT AVG(Percentage) FROM Result);

-- IN subquery: students in CS courses
SELECT RollNo, Name FROM Student
WHERE RollNo IN (
    SELECT DISTINCT RollNo FROM Enroll
    WHERE CourseID LIKE 'CS%'
);

-- Correlated subquery: above branch-wise average
SELECT s.Name, r.Branch, r.Percentage
FROM Result r JOIN Student s ON s.RollNo = r.RollNo
WHERE r.Percentage > (
    SELECT AVG(r2.Percentage)
    FROM Result r2
    WHERE r2.Branch = r.Branch  -- re-runs for each outer row
);

❓ Viva & FAQ — Chapter 6

WHERE filters individual rows BEFORE grouping. HAVING filters groups AFTER aggregation. HAVING can use aggregate functions; WHERE cannot.

UNION removes duplicate rows and returns only distinct rows. UNION ALL retains all rows including duplicates. UNION ALL is faster.

A correlated subquery references a column from the outer query. It re-executes for each row processed by the outer query (e.g., comparing each student to their branch's average).

Outer joins return NULLs for unmatched rows. LEFT JOIN → right side NULLs. RIGHT JOIN → left side NULLs. FULL OUTER JOIN → both sides can have NULLs. INNER JOIN never returns NULLs.
